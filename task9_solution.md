# Задание 9. Настройка чтения с реплик и консистентность

## Общие правила

Не все чтения можно отправлять на secondary. Там данные могут отставать от primary, поэтому:

- чтения, влияющие на деньги, остатки, оформление заказа и текущий статус, идут на `primary`;
- чтения каталога, истории и аналитики могут идти на `secondary`, если небольшая задержка приемлема;
- для secondary используем `readPreference: secondaryPreferred` или `nearest`, но с ограничением `maxStalenessSeconds`.

Базовая настройка для чтений, где допустимо небольшое отставание:

```javascript
db.getMongo().setReadPref("secondaryPreferred")
```

## Таблица операций

| Коллекция | Операция чтения | Где читать | Допустимая задержка | Почему |
| --- | --- | --- | --- | --- |
| `products` | Карточка товара: название, описание, атрибуты | secondaryPreferred | до `30-60 сек` | Описание товара меняется редко, небольшое отставание не критично |
| `products` | Список товаров категории и фильтр по цене | secondaryPreferred + cache | до `30-60 сек` | Каталог читается часто, можно разгрузить primary и Redis дополнительно сгладит нагрузку |
| `products` | Остаток перед показом кнопки покупки | primaryPreferred | до `5 сек`, лучше меньше | Небольшая неточность в интерфейсе допустима, но лучше не показывать явно недоступный товар |
| `products` | Остаток перед созданием заказа и списанием | primary | `0 сек` | Нельзя продать товар, которого уже нет |
| `products` | Проверка цены при оформлении заказа | primary | `0 сек` | Цена в заказе должна быть актуальной |
| `products` | Поиск и рекомендации | secondaryPreferred | до `60-120 сек` | Не влияет напрямую на деньги и остатки |
| `orders` | История заказов пользователя | secondaryPreferred | до `10-30 сек` | Пользователь может увидеть новый заказ с небольшой задержкой, это не ломает оформление |
| `orders` | Статус только что созданного заказа | primary | `0 сек` | После оплаты или оформления нельзя показать старый статус |
| `orders` | Страница деталей заказа | primaryPreferred | до `5-10 сек` | Обычно нужна свежая информация, но для старых заказов можно читать с secondary |
| `orders` | Внутренняя отчетность по заказам | secondary | до `5-10 мин` | Аналитика не должна мешать пользовательским операциям |
| `carts` | Получение активной корзины | primary | `0 сек` | Корзина часто меняется, пользователь должен видеть последнее действие |
| `carts` | Проверка корзины перед оформлением заказа | primary | `0 сек` | Состав корзины должен совпадать с тем, что оформляется |
| `carts` | Просмотр брошенных корзин для маркетинга | secondary | до `5-10 мин` | Маркетинговая обработка не требует мгновенной актуальности |
| `carts` | TTL/служебная очистка старых корзин | primary | `0 сек` | Удаление и изменение состояния выполняются на primary |

## Обоснование по коллекциям

### products

`products` читается очень часто, особенно каталог и карточки товара. Эти операции можно отдавать с secondary, потому что описание, фото, характеристики и список товаров не требуют строгой консистентности.

Остатки и цена при оформлении заказа читаются только с primary. Тут риск уже бизнесовый: если прочитать устаревший остаток с secondary, можно принять заказ на товар, которого нет. Поэтому перед списанием остатка операция должна идти на primary и лучше выполняться атомарно через условный update:

```javascript
db.products.updateOne(
  {
    category_id: "electronics",
    product_id: "product_100",
    "stock_by_geo_zone.geo_zone": "msk",
    "stock_by_geo_zone.quantity": { $gt: 0 }
  },
  {
    $inc: { "stock_by_geo_zone.$.quantity": -1 },
    $set: { updated_at: new Date() }
  }
)
```

### orders

Для истории заказов можно использовать secondary: если заказ появится в истории через несколько секунд, это терпимо. Но статус нового или оплаченного заказа должен читаться с primary, потому что устаревший статус может вызвать повторную оплату, лишнее обращение в поддержку или неправильное поведение фронта.

Для отчетов лучше всегда использовать secondary, чтобы тяжелые выборки не мешали созданию заказов.

### carts

Корзина самая чувствительная к свежести. Пользователь добавил товар и сразу ожидает увидеть его в корзине. Если прочитать с отстающей secondary, товар может пропасть на несколько секунд. Поэтому активная корзина, изменение корзины и оформление заказа идут через primary.

С secondary можно читать только неоперативные данные: брошенные корзины, маркетинговые выгрузки, статистику.

## Настройки read concern

Для критичных чтений:

```javascript
db.runCommand({
  find: "orders",
  filter: { order_id: "ord_1000001" },
  readConcern: { level: "majority" }
})
```

Для чтений с secondary можно ограничить отставание:

```javascript
MongoClient(
  "mongodb://mongos:27017/?readPreference=secondaryPreferred&maxStalenessSeconds=90"
)
```

Для отчетности:

```javascript
db.getMongo().setReadPref("secondary")
db.orders.find({ created_at: { $gte: ISODate("2026-08-01") } })
```
