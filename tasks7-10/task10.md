## Миграция на Cassandra

### Задание 1
Кассандра очень хорошо справляется с большим количеством запросов на запись, благодаря ее хранилищу реализованному через `LSM` дерево. С чтением тоже довольно хорошо справляется, если они в рамках одной партиции. Но вот со сложными условиями, джоинами, `acid` транзакциями и чтением из разных партиций эффективность чтения снижается. Под такие характеристики больше всего подходят:
* история заказов (в виде read модели)
* пользовательские сессии
* и, наверное, корзины

Заказы и товары не совсем подходят, потому что для них нужны строгие гарантии консистентности, атомарность изменений и зачастую их читают сложными джоинами и условиями на несколько колонок (которые с большой вероятностью будут лежать в разных партициях). У товаров еще не очень строгая схема данных, то есть у разных товаров могут лежать разные значения в документах Монги. 

К примеру, заказу нужно менять статус, как-то фиксировать цены, создавать платежные операции и все это требует строгой согласованности и транзакционности, которые ограниченно поддержаны в Кассандре (только в рамках одной партиции). Поэтому лучше оставить их в Монго.

Идеальный кандидат - это пользовательские сессии. Вытаскивать из базы их будем строго по первичному ключу (`session_id`) без какой-то сторонней логики, что позволит их всегда читать из одной партициии. В Кассандре также поддержан `ttl` для каждой отдельной записи. Данные также отлично шардируются благодаря рандомному `session_id`, который поспособствует равномерному распределению по шардам.

История заказов тоже неплохой вариант, если рассматривать ее как денормализованную read модель. Данные также будут читаться равномерно по идентификатору, без лишних джоинов, что позволит их быстро вытаскивать из единой партиции (или из небольшого множества партиций, если сделаем составной ключ для партицирования)

Корзина уже более спорный вариант для миграции на Кассандру, но тоже вполне возможен. Смущает немного более строгии гарантии к этой сущности, т.к. при ее изменении она всегда должна показывать актуально добавленные товары (как в рамках одного устройства, так и на разных). Также довольно сложный сценарий со слиянием корзин (гостевая мержится с пользовательской), т.к. если они будут находиться в разных партициях, то это станет не очень оптимальной операцией. Но все же решение конфликтов возможен, т.к. last writes win здесь вполне адекватен.

Помимо этого в Кассандру можно еще мигрировать таблицу с пользовательскими ивентами (если бы такая была). Данные там как раз совсем не меняются, а только добавляются. По хорошо подобранному ключу партицирования эти данные также очень удобно будет вытаскивать в больших количествах.

### Задание 2

#### Пользовательские сессии:

Таблица
```
CREATE TABLE user_sessions_by_id (
    session_id text,
    user_id uuid,
    created_at timestamp,
    expires_at timestamp,
    device_id text,

    PRIMARY KEY ((session_id))
);
```

Здесь ключом партиционирования является `session_id`, а ключа для кластеризации нет, т.к. обращаемся а базу за единсвтенной сессией только с айдишником.
Благодаря высокой кардинальности ключа, данные будут хорошо распределны между всеми шардами и риск появления "горячих" партиций минимален.

Но также можем сделать отдельную таблицу для получения сессий, сгрупированных по user_id
```
CREATE TABLE user_sessions_by_user_id (
    session_id text,
    user_id uuid,
    created_at timestamp,
    expires_at timestamp,
    device_id text,

    PRIMARY KEY (
        (user_id),
        created_at
    )
)

WITH CLUSTERING ORDER BY (
    created_at DESC
);
```

#### История заказов

Обычно историю запрашивают по какому-то конкретному пользователю за какой-то промежуток времени. Исходя из этого можно сделать такую табличку:
```
CREATE TABLE orders_by_customer_month (
    customer_id uuid,
    order_month date,
    created_at timestamp,
    order_id uuid,
    status text,
    total decimal,
    currency text,
    items_count int,

    PRIMARY KEY (
        (customer_id, order_month),
        created_at,
        order_id
    )
)
WITH CLUSTERING ORDER BY (
    created_at DESC,
    order_id ASC
);
```

В ключе партиции есть `customer_id` и `order_month`, чтобы заказы пользователя за каждый месяц лежали в своей партиции. Если бы был только `customer_id`, то партиции были бы перегружены.

В качестве ключа кластеризации добавил `created_at` для удобства сортировки и `order_id`, чтобы решать возможные коллизии.

Тут вероятность появления "горячих" партиций выше (из-за какого-нибудь корпоративного заказчика) - их можно устранить заменой `order_month` на `order_day` в ключе партиционирования

#### Корзина

Обычно запрашивается все содержимое конкретной корзины, поэтому табличка выглядела бы так:
```
CREATE TABLE cart_items_by_cart_id (
    cart_id uuid,
    user_id uuid,
    updated_at timestamp,
    product_id uuid,
    sku text,
    quantity int,
    added_at timestamp,

    PRIMARY KEY (
        (cart_id),
        product_id
    )
)
```

Ключом партицирования является `cart_id`, что позволит равномерно распределить корзины по шардам. А ключ кластеризации - `product_id`, т.к. без него в корзине мог бы быть только один товар.

Корзина обычно немного товаров содержит, поэтому риск появления "горячей" партиции не очень велик.


#### Пользовательские события

Хочется вытаскивать все события конкретно пользователя за определенный промежуток времени:
```
CREATE TABLE ecommerce.user_events_by_user_day (
    user_id uuid,
    event_day date,
    occurred_at timeuuid,
    session_token_hash text,
    event_type text,
    product_id uuid,
    metadata_json text,

    PRIMARY KEY (
        (user_id, event_day),
        occurred_at
    )
)
WITH CLUSTERING ORDER BY (
    occurred_at DESC
)
AND default_time_to_live = 2592000; // 30 дней
```

Здесь в ключе партиционирования `user_id` связывает все события одного пользователя, а `event_day` распределяет их по партициям.

Ключ кластеризации `occurred_at` с типом `timeuuid`, а не `timestamp`, чтобы не было коллизий (если в одно и то же время совершилось несколько ивентов).

Тут не ожидается дикой активности от пользователя, из-за которой могла бы возникнуть "горячая" партиция, но всегда можно использовать `event_hour`, вместо `event_day`


### Задание 3

Важно подметить, что перечисленные три стратегии: Hinted Handoff, Read Repair, Anti-Entropy Repair - не взаимоисключающие вещи. Они служат для синхронизации данных по разным флоу:
* Hinted Handoff больше для случаев записи
* Read Repair восстанавливает данные при чтении, если нода замечает, что у какой-то реплики старые данные
* Anti-Entropy Repair по-хорошему лучше всегда включать, чтобы поддерживать консистентность таблиц во всех сценариях

Итоговая таблица по стратегиями и уровням гарантий согласованности:

| Сущность | Запись | Чтение | Read Repair | Hinted Handoff | Anti-Entropy Repair |
|---|---|---|---|---|---|
| Пользовательские сессии | `LOCAL_QUORUM` | `LOCAL_QUORUM` | `BLOCKING` | Включён | Частый |
| История заказов | `LOCAL_QUORUM` | `LOCAL_QUORUM` | `BLOCKING` | Включён | Регулярный |
| Корзины | `LOCAL_QUORUM` | `LOCAL_QUORUM` | `BLOCKING` | Включён | Частый |
| Пользовательские события | `LOCAL_ONE` или `LOCAL_QUORUM` | `LOCAL_ONE` | `NONE` | Включён | Регулярный |

#### Пользовательские сессии

Для сессий актуальность данных достаточно важна. После логаута или блокировки юзера система не должна продолжать принимать старую сессию только потому, что запрос попал на отставшую реплику.

Сессия читается часто, поэтому read repair с типом `blocking` отлично подходит для обнаружения отставших реплик. 
Anti-entropy repair тоже очень важен, т.к. у сессий есть ttl и поэтому до отозванных сессий просто можно не достучаться.

`LOCAL_QUORUM` гарантирует схождение реплик только в рамках одного ДЦ. Если пользователь может как-то резко обращаться к сессии из других регионов, то лучше тогда сделать `EACH_QUORUM`, чтобы синхронизация реплик происходила также между ДЦ.

#### История заказов

Read repair с дефолтным `BLOCKING` добавляет небольшое `latency` для запросов, но зато будет всегда возвращаться наиболее свежая версия данных.

Если же небольшое отставание данных допустимо, то можем сделать read repair `none` (чтобы не блочило), а также `LOCAL_QUORUM` поменять на `LOCAL_ONE`, для которого нужно подтврждение только с одной реплики


#### Корзины

Пользователь после добавления товара ожидает сразу увидеть его в корзине. `LOCAL_QUORUM` снижает вероятность чтения версии, которая не содержит только что выполненное изменение.

Hinted Handoff также полезен, если одна реплика временно недоступна во время добавления или удаления товара. Anti-Entropy Repair необходимо выполнять часто, поскольку корзины содержат обновления и удаления.

#### Пользовательские события

Здесь у нас таблицы содержат преимущественно append only события. Для них допустима временная рассинхронизация реплик, поэтому вполне валидно использовать `LOCAL_ONE` и `none` для read repair.

Некоторые ивенты могут вообще никогда не быть прочитаны. Поэтому read repair не сможет обнаружить расхождения. Anti-Entropy repair должен периодически проверять реплики.
