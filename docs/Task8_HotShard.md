# Задание 8. Выявление и устранение «горячих» шардов

Предполагается, что коллекция "Товары" [products] шардируется по категориям, и из-за большей популярности кавтегории "Электроника" количество запросов на определённый шард выросло.
Также предположу, что вся категория оказалась на одном шарде.

## Метрики, помогающие выявить "горячие" шарды
Не хочу делать слишком много метрик, поэтому вот 6, которые можно будет объединить в одну.

| № | Метрика              | Комментарий                                                                                                                                                                                                                    | Порог                              |
|---|----------------------|--------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|------------------------------------|
| 1 | RPS                  | тут можно выявить самый загруженный шард. Косвенно может помочь определить горячий шард, если запросов к одному сильно больше, чем к остальным, `db.serverStatus().opcounters` метрика `query`                                 | Отклонение > 30 % от среднего      |
| 2 | CPU utilization      | тоже надо смотреть на шард, загрузка которого заметно выше, чем у остальных, также можно использовать и пороговое значение, так как если у всех будет примерно одинаковый результат, то можно не заметить, что перегружены все | > 80% при среднем 30 % по кластеру |
| 3 | p95 latency          | если задержки запросов к какому-то шарду аномально высокие, то скорее всего он и есть искомый<br/>`db.serverStatus().opLatencies`, метрика `reads`                                                                             | > 100 мс                           |
| 4 | Распределение чанков | Вообще это зависит от алгоритма, если алгоритм не распределённый, может ввести в заблуждение. `db.products.getShardDistribution()`                                                                                             | > 50% чанков на шарде              |
| 5 | Disc IOPS            | может показать, что файловая система перегружена, также если показатель аномально высокий, может свидетельствовать о перегрузке                                                                                                | > 80%                              |
| 6 | Slow queries         | также если показатель аномально высокий, может свидетельствовать о перегрузке<br/>`db.setProfilingLevel(1, { slowms: 30 })` `db.system.profile.find().sort({ millis: -1 })`                                                    | > 50 мс                            |


Ручная диагностика может быть следующей:
1. Распределение данных по шардам
  ```js
  db.products.getShardDistribution()
  ```
2. Состояние балансировщика
  ```js
  sh.status()
  ```
3. Тяжёлые операции или медленные запросы
  ```js
  db.currentOp({ "secs_running": { $gt: 1 } })
  ```
  ```js
  db.system.profile.find().sort({ millis: -1 }).limit(5)
  ```

## Механизмы автоматического перераспределения данных
- Включить балансировщик, если он не включен
    ```js
    sh.startBalancer()
    ```
- Настроить временное окно балансировки на внепиковые периоды
  ```js
    use config
    db.settings.updateOne(
    { _id: "balancer" },
    { $set: { activeWindow: { start: "02:00", stop: "06:00" } } },
    { upsert: true }
    )
    ```
Если диапазон "Электроника" представляет собой один чанк, то балансировщик не поможет, но можно попробовать
- уменьшить размер чанка, чтобы произошло автоматическое разбиение
  ```js
  sh.updateChunkSize("shop.products", 10) //10 Mb
  ```
  Это плохое решение, так как спасёт только временно, а на больших объёмах может перегрузить балансировщик

- Включить режим Read Replica, если загружен Primary реплика.
    ```js
    db.getMongo().setReadPref("secondaryPreferred")
    ```
  - Сделать больше реплик, это может распределить по ним запросы, но ухудшит консистентность
- Использовать Zone Sharding, чтобы вручную раскидать одну категорию по нескольким шардам, но это будет работать только если категория уже разбита на несколько чанков
  ```js
  sh.addShardToZone("shard1", "electronics")
  sh.addShardToZone("shard2", "electronics")
  sh.addShardToZone("shard3", "electronics")
  
  sh.updateZoneKeyRange(
  "shop.products",
  { category: "Электроника" },
  { category: "Электроника" },
  "electronics"
  )
  ```
- Изменить алгоритм шардирования
- Если нет кэширования, то подключить кэширование
