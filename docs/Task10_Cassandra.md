# Задание 10. Миграция на Cassandra: модель данных, стратегии репликации и шардирования

## Задание 10.1
У MongoDb сейчас присутствует проблема перераспределения данных при масштабировании при добавлении новых шардов, что вызывает высокую нагрузку и просадки latency.
В Cassandra при добавлении ноды используется consistent hashing с vnodes, партиции не разрезаются и не переливаются между всеми узлами кластера. Это исключает просадку latency, которая была в MongoDB при полной перебалансировке чанков.

### Кандидаты на миграцию
| Коллекция/данные | Обоснование                                                                                                                                                                  | Комментарий                                                                                            |
|------------------|------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|--------------------------------------------------------------------------------------------------------|
| `carts`          | Мелкие короткоживущие объекты с частыми обновлениями (добавление/удаление товаров) и TTL для abandoned корзин, при объединении корзин можно требовать Consistency Level ALL. | активная корзина требует консистентности (CL: `QUORUM` на чтение и запись)                             |
| события аудита   | Частые операции записи, объекты не меняются                                                                                                                                  | eventual consistency приемлема, так как это просто лог<br/>CL: `ONE` на чтение и `LOCAL_ONE` на запись |
| `order_events`   | Частые операции записи, объекты не меняются. Частный случай событий аудита.                                                                                                  | CL: `ONE` на чтение и `LOCAL_ONE` на запись                                                            |

### Оставить вне Cassandra

| Коллекция               | Причина оставить на текущей платформе                                                                                                                                                                                                                                                                                                                                                                                     |
|-------------------------|---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| `products`              | Остатки товаров требуют согласованности при создании заказа (списании остатков, чтобы не продать отсутствующий товар), чего не может обеспечить Cassandra, также она не обеспечивает необходимый уровень ACID для операций, связанных со складскими остатками при нагрузке 50 000 запросов/сек без критических просадок latency.<br/>Для MongoDb необходимо выделить кластерные ключи                                     |
| `orders`                | Требуется обеспечение трензакционной согласованности с остатками на складе.<br/>Каталог может переехать в Cassandra, если будет разделение на номенклату и остатки на складе. Справочник товаров таким образом может быть перенесён в Cassandra при условии, что при создании заказа взаимодействие будет происходить со складскими остатками. Также можно рассмотреть использование распределённых транзакции в будущем. |
| Пользовательские сессии | Пользовательские сессии лучше себя чувствуют в Redis, если это не какие-то сложные объекты с большим временем жизни, а небольшие key-value объекты с коротким TTL.                                                                                                                                                                                                                                                        |

## Задание 10.2
Partition key определяет, на какой ноде лежат данные.  
Clustering key сортирует данные внутри партиции

1. carts

```cassandraql
CREATE TABLE carts (
    owner_id TEXT,
    cart_id UUID,
    status TEXT,
    items LIST<FROZEN<map<UUID, INT>>>,
    created_at TIMESTAMP,
    updated_at TIMESTAMP,
    expires_at TIMESTAMP,
    PRIMARY KEY (owner_id, cart_id)
) WITH read_repair = 'NONE'
  AND default_time_to_live = 86400;
```
Здесь `owner_id` – это user_id или session_id
В качестве partition key выступает `owner_id`, чтобы запрос по пользователю всегда попадал на один шард.
В случае, если у пользователя несколько корзин, то можно сделать `cart_id` кластерным ключом. Однако в текущей задачи у пользователя одна активная корзина.

2. События аудита, например, `order_events`
```cassandraql
CREATE TABLE order_events (
    order_id UUID,
    event_date DATE,
    event_time TIMESTAMP,
    event_type TEXT,
    PRIMARY KEY ((order_id, event_date), event_time)
) WITH read_repair = 'NONE'
  AND compaction = {'class': 'TimeWindowCompactionStrategy',
                    'compaction_window_unit': 'DAYS',
                    'compaction_window_size': 1};
```
Напрашивается выделение partition key как (order_id, event_date) для запросов по заказу, однако в зависимости от требований можно поменять порядок ключей. Для cluster key используется timestamp, что дополнительно поможет с выборкой по времени.
Если потребуется читать события по времени без привязки к order_id, стоит добавить вторичную таблицу с PK (event_date, event_time).

3. orders
Остаётся в mongodb.
В качестве оптимизации стоит использовать составной ключ.
```js
db.orders.createIndex({ user_id: 1, year_month: 1, order_id: 1 }, { unique: true })
```
Нужно при этом убедиться, что вычисляемое поле `year_month` содержится в схеме и генерируется приложением.

Потом можно разделить соответственно по шардам
```js
sh.shardCollection("somedb.orders", { user_id: 1, year_month: 1 })
```

4. products
Остаётся в mongodb.
Можно рассмотреть в качестве оптимизации выделение каталога товаров для просмотра в Cassandra, а для операций с остатками использовать MongoDb.
При этом если шарды MongoDb по продуктам уже перегружены, можно рассмотреть использование составного ключа
```js
db.products.createIndex({ category_id: 1, product_id: 1 }, { unique: true })
```

## Задание 10.3
Для всех сущностей при записи используется Hinted Handoff (включен для кластера). Это может эффективно работать, если нода недоступна не сильно большое время (3 часа по умолчанию). Это не решает проблему согласованности на момент чтения, а является одним из механизмов обеспечения eventual consistency.

Также для случаев, когда нода падает на большое время, нужно запускать Anti-Entropy Repair.
1. Для корзин `carts` в Read Repair необходимости нет, так как объединение корзин – относительно редкая операция, и отсутствие Read Repair позволит снизить latency на все операции чтения, а при объединении читать с CL=`ALL`
2. События аудита (или события заказа `order_events`). Read Repair не нужен, так как чтение происходит редко, а самое главное, что на момент чтения самая актуальная информация не нужна, eventual consistency приемлема, а Read Repair неоправданно затратен. 

Anti-Entropy Repair используется после длительной недоступности узла, либо по расписанию. Можно определить примерно следующее расписание:

| Сущность                                           | Частота восстановления | Комментарий                                                                                                       |
|----------------------------------------------------|------------------------|-------------------------------------------------------------------------------------------------------------------|
| carts                                              | Раз в 1-2 недели       | Данные временные, за исключением редких объединений корзин потребность в самых актуальных данных не такая высокая |
| События аудита (или события заказа `order_events`) | Раз в месяц            | Чтение редкое, необходимость в самых актуальных данных ниже, чем для других сущностей                             |

Запуск восстановления для разных таблиц лучше делать в разное время, иначе может сильно вырасти нагрузка на сеть и диски.
