## Контекст

«Мобильный мир» вырос: теперь помимо аксессуаров продаются электроника, аудио- и бытовая
техника и другие категории. Бэкенд хранит `orders`, `products`, `carts` в MongoDB (шардированной
и реплицированной — см. предыдущий блок). Во время «чёрной пятницы» шардирование по диапазонам
не справилось с резким ростом нагрузки (50 000 запросов/сек): при добавлении шардов MongoDB
полностью перераспределяла данные, что просаживало latency в пик. Руководство рассматривает
частичную миграцию критичных данных на Cassandra.

Работа сдаётся как единый архитектурный документ (не как код/PR) — согласно инструкции
«Как сдать работу» для заданий 7–10, без требования отдельного пул-реквеста.

## Задание 7 — Проектирование схем коллекций

**`orders`** — шард-ключ `{customer_id: "hashed"}`.
- Атрибуты: `order_id`, `customer_id`, `order_datetime`, `items[]` (со `price` на момент заказа),
  `status`, `total`, `geo_zone`.
- Обоснование: равномерное распределение записи новых заказов (частая операция); «история
  заказов пользователя» — точечный запрос к одному шарду вместо scatter-gather; `geo_zone`
  сознательно не в ключе — иначе те же риски hot-шарда, что и у `products` (см. ниже), а
  geo-аналитика не входит в перечисленные частые операции.
- Пример: `sh.shardCollection("mobilnyMir.orders", { customer_id: "hashed" })`.

**`products`** — составной шард-ключ `{category: 1, product_id: "hashed"}`.
- Атрибуты: `product_id`, `name`, `category`, `price`, `stock_by_geozone: {geozone: qty}`,
  `attributes: {color, size, ...}`.
- Обоснование: range по `category` — быстрый поиск/фильтр по категории и диапазону цен (частая
  операция); hashed-суффикс по `product_id` не даёт одной категории (например, «Электроника»)
  осесть на одном шарде целиком — структурная защита от hot-шарда, которая прямо ведёт к
  заданию 8. Обновление остатков (`stock_by_geozone`) маршрутизируется по тому же ключу, частота
  обновлений на выбор ключа не влияет.
- Пример: `sh.shardCollection("mobilnyMir.products", { category: 1, product_id: "hashed" })`.

**`carts`** — единый `owner_key` (=`user_id`, если пользователь залогинен, иначе `session_id`),
шард-ключ `{owner_key: "hashed"}`.
- Атрибуты: `_id`, `user_id`/`session_id`, `items: [{product_id, quantity}]`, `status`,
  `created_at`, `updated_at`, `expires_at` (TTL).
- Обоснование: «текущая корзина гостя/пользователя» всегда точечный запрос по `owner_key`
  независимо от статуса логина. Слияние корзин при логине — последовательность из двух
  точечных операций на разных значениях `owner_key` (не атомарная кросс-шардовая транзакция;
  явно описываю компромисс).
- Пример: `sh.shardCollection("mobilnyMir.carts", { owner_key: "hashed" })`.

## Задание 8 — Hot shards

**Метрики мониторинга:**
- Per-shard ops/sec (read/write раздельно), число и размер чанков на шард (`sh.status()`,
  `config.chunks`), replication lag на репликах шарда, WiredTiger cache eviction rate, доля
  медленных запросов на шард (`system.profile`), % сетевых соединений/lock-time на шард.
- Бизнес-метрика: доля трафика по категориям (Prometheus/Grafana), алерт при отклонении
  ops/sec шарда от среднего более чем в 1.5–2 раза на устойчивом окне.

**Механизмы устранения:**
1. Составной shard-key с hashed-суффиксом (уже заложен в задании 7).
2. Zone sharding — выделить «горячей» категории больше зон/шардов
   (`sh.addShardToZone`, `sh.updateZoneKeyRange`).
3. `sh.splitAt` / `sh.moveChunk` — ручное/усиленное автоматическое перераспределение чанков.
4. Redis-кеш перед горячей категорией для read-hot паттернов (прямая отсылка к уже
   реализованному кешированию в блоке заданий 1–6).

## Задание 9 — Read preference

Таблица: коллекция × операция × `primary`/`secondary` × допустимая задержка репликации,
с обоснованием по каждой строке. Примеры строк:
- Остаток товара перед оплатой → `primary` (риск перепродажи).
- Листинг/поиск товаров по категории → `secondary`, до ~5–10 с (цены/остатки меняются нечасто).
- Создание заказа + немедленное подтверждение → `primary` (read-your-write).
- История старых заказов → `secondary`, до ~30 с.
- Активная корзина и слияние корзин при логине → `primary` (иначе баги вида «пропавший товар»).
- Фоновая очистка просроченных/абандон корзин → `secondary`, минуты — не критично.

## Задание 10 — Миграция на Cassandra

**10.1 Что переносим:**
- `orders` (история + статус) — высокая частота записи в пик, естественный time-series доступ,
  нужна масштабируемость записи; целостность обеспечивается тюнингом consistency level (QUORUM),
  а не исключается переходом на Cassandra.
- `carts` / пользовательские сессии — очень высокая частота записи/чтения, естественный TTL,
  ценность geo-распределённой leaderless-репликации при росте магазина.
- **Остаётся в MongoDB:** `products` — нужны гибкие фильтры по категории/цене; это сильная
  сторона MongoDB, в Cassandra (query-first моделирование) такие ad hoc фильтры неудобны.

**10.2 Концептуальная модель** (денормализация под паттерн доступа, как принято в Cassandra):
- `orders_by_customer`: partition key `(customer_id, year_month)` (бакетирование по месяцу —
  избегаем неограниченного роста партиции активного клиента), clustering key
  `order_datetime DESC, order_id` — под «история заказов пользователя».
- `orders_by_id`: partition key `order_id` — под «статус конкретного заказа».
- `cart_items`: partition key `owner_key` (тот же принцип, что и в MongoDB-дизайне задания 7),
  clustering key `product_id`, `TTL` на строку — под точечное добавление/удаление товара без
  read-modify-write всего документа корзины.
- Обоснование через consistent hashing: добавление узла в кольцо Cassandra двигает только
  соседние диапазоны токенов — в отличие от полного перераспределения MongoDB при
  range-шардировании, вызвавшего просадку latency в исходном инциденте.

**10.3 Стратегии восстановления целостности:**
- Hinted Handoff — включён по умолчанию для всех таблиц (сохраняет доступность записи при
  кратковременной недоступности реплики).
- Read Repair — усилен (`read_repair_chance`) для `orders_by_*`: заказы часто перечитываются
  сразу после записи (страница подтверждения), самолечение почти бесплатно.
- Anti-Entropy Repair (`nodetool repair`) — чаще для `cart_items` из-за churn от TTL-tombstone'ов
  (частота ремонта должна укладываться в `gc_grace_seconds`, иначе риск «воскрешения» удалённых
  данных).
- Consistency level: `QUORUM`/`QUORUM` для `orders_*` (целостность важнее задержки); `LOCAL_ONE`
  / `LOCAL_QUORUM` для `cart_items` (задержка важнее строгой консистентности, staleness
  собственной корзины между устройствами — редкий и не критичный случай).
